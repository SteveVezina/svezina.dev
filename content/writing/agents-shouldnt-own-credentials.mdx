The first production question I ask about an agent is not which model it uses.

It is: **what authority does this process wake up with?**

Give an agent a real job and credentials appear almost immediately. It may need to read source code, call a model, query a database, open an issue, send a message, or deploy software. The usual application pattern is to put those credentials in environment variables and start the process:

```env
OPENAI_API_KEY=...
GITHUB_TOKEN=...
DATABASE_URL=...
```

That is convenient. It is also a strange default for software whose defining feature is that it can inspect untrusted input and decide what to do next.

> **Useful agents need capabilities. They do not need to own the credentials behind those capabilities.**

![Credential ownership versus delegated capability](/writing/credential-path.svg)

This post is the first in a series about treating agents as infrastructure rather than unusually clever application processes. The experiment is intentionally small: prove the security boundary first, then make the runtime more capable.

## A small experiment with a useful boundary

**[Deploy the experiment →](https://vercel.com/new/clone?repository-url=https%3A%2F%2Fgithub.com%2FSteveVezina%2Fagent-snippets&root-directory=secretless-agent&project-name=secretless-repo-analyst)**

The runnable example lives in [`SteveVezina/agent-snippets`](https://github.com/SteveVezina/agent-snippets/tree/main/secretless-agent), separate from this blog.

Its job is deliberately narrow: give it a **public GitHub repository URL** and it returns an architecture and risk briefing.

The application needs two powerful things: somewhere isolated to inspect arbitrary code and a model capable of reasoning about what it finds. It does not need a permanent GitHub credential because the repository is public. More importantly, the deployed application does not need a long-lived OpenAI or Anthropic key either. [Vercel AI Gateway can authenticate Vercel workloads with OIDC](https://vercel.com/docs/ai-gateway/authentication-and-byok), so the workload can use its platform identity rather than carrying another provider secret.

Repository inspection happens inside [Vercel Sandbox](https://vercel.com/docs/sandbox), an ephemeral isolated environment intended for running untrusted and AI-generated code.

```text
browser
  │
  ▼
Next.js route
  │
  ├── Vercel Sandbox ── clone + inspect repository
  │
  └── AI Gateway ────── architecture + risk briefing
            ▲
            │
       workload identity
```

This is not a complete agent security architecture. It demonstrates one property I want to preserve as the system grows:

**the reasoning process should begin with less authority than the total set of actions the product may eventually perform.**

## The risk is not only secret theft

Traditional secret management asks whether an attacker can read a credential.

Agents introduce a second question:

> Can untrusted context cause the credential holder to *use* its authority incorrectly?

That distinction matters because agents consume instructions from users, documents, websites, repositories, tool results, memory, and other agents. Some of those inputs are untrusted, yet they can influence the next action.

If the same process interpreting that content also holds a broad, long-lived token, an attacker may not need to exfiltrate the token. The attacker can try to manipulate the privileged process into exercising authority on their behalf.

This is the confused deputy problem with a reasoning loop attached.

OWASP's [AI Agent Security guidance](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) recommends least privilege, per-tool permission scoping, explicit authorization for sensitive operations, sandboxing, and separation between decision-making and irreversible execution. Its [prompt injection guidance](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html) similarly treats external content as hostile and emphasizes limiting the authority available to the model-driven path.

The architectural conclusion is stronger than "store your secrets safely":

> **The model should not be the authorization boundary.**

## A vault solves custody, not authority

Moving `GITHUB_TOKEN` from source code into a secret manager is unquestionably better than committing it to a repository.

But once that token is injected into an agent process, the process still possesses its authority.

A vault answers:

```text
Where is the credential stored?
```

An agent architecture must also answer:

```text
Who can request it?
For which action?
For which resource?
For how long?
Under whose authority?
Can the request be denied independently of the model?
```

Those are authorization questions, not secret-storage questions.

The better optimization target is therefore:

> **How little authority can exist inside the agent, for how little time?**

## Identity first, credential second

Cloud infrastructure already has a useful pattern for this.

A workload proves its identity. Policy evaluates what that identity may do. A short-lived credential or capability is produced only when it is needed.

```text
workload identity
      │
      ▼
authorization policy
      │
      ▼
short-lived capability
      │
      ▼
one bounded action
```

That is materially different from starting a process with a bag of credentials representing every action it might ever perform.

[Vercel Connect](https://vercel.com/blog/introducing-vercel-connect) applies this idea to external services: a Vercel workload can use OIDC to request short-lived credentials instead of keeping provider credentials permanently in application configuration. Cloud IAM systems have been moving in the same direction for workloads for years, and are increasingly applying those identity concepts to agents as first-class actors.

The specific implementation will vary by platform. The invariant is more important:

**identity and policy should precede credential issuance.**

## Separate reasoning from authority

As an agent becomes useful, it accumulates capabilities: source control, databases, ticketing systems, chat, cloud APIs, production telemetry, deployment systems.

If each new integration becomes another permanent secret in the same runtime, one process eventually owns three very different responsibilities:

1. interpreting potentially hostile context,
2. deciding what action should happen,
3. holding the credentials that make the action possible.

That is too much trust in one boundary.

A more defensible decomposition looks boring, which is a feature:

```text
reasoning loop
     │ proposes an action
     ▼
authorization / policy
     │ grants a bounded capability
     ▼
execution boundary
     │ performs the action
     ▼
external system
```

The responsibilities become explicit:

- **Reasoning** decides what should happen.
- **Execution** runs code in an isolated environment with bounded filesystem and network access.
- **Identity** establishes which workload or user is acting.
- **Authorization** applies deterministic policy outside the model.
- **Credential exchange** resolves short-lived authority only when required.
- **Approval** gates destructive or high-blast-radius operations.
- **Audit** records the identity, requested capability, policy decision, and resulting action.

The goal is not to eliminate secrets from computing. It is to stop the autonomous reasoning process from becoming their permanent owner.

## Secretless does not mean secret-free

The word *secretless* is easy to oversell.

For this experiment it means something narrower and testable:

> **The deployed agent application stores no long-lived model-provider credential.**

Secrets still exist elsewhere. OAuth providers maintain credentials. Infrastructure platforms maintain signing keys. Credential brokers may hold sensitive configuration. Some legacy APIs accept nothing better than static API keys. Local development may also require a development credential.

The architecture improves when those limitations sit behind an identity and policy boundary instead of being copied into every agent runtime.

This is why "secretless" is best understood as a direction of travel: reduce ambient credentials inside the reasoning and execution path, shorten credential lifetime, narrow scope, and make authority explicit at the moment of action.

## Think in an authority ladder

Not every tool call needs the same mechanism.

```text
LOWER RISK
│
├─ public data                 no credential
├─ internal read               scoped workload identity
├─ user data                   delegated user authority
├─ reversible write           short-lived capability + policy
├─ destructive / external     capability + policy + approval
│
HIGHER RISK
```

An agent can have a broad **reasoning horizon** while retaining a narrow **execution horizon**.

That distinction is useful. We want models to consider many possibilities. We do not need every possibility pre-authorized.

## What this demo does not prove

The example uses a public GitHub repository, so it deliberately avoids claiming to have solved private repository authorization.

It also does not yet include:

- delegated access to a private repository,
- a human approval step,
- an arbitrary SaaS credential broker,
- fine-grained network policy for every tool,
- a complete audit trail across all actions.

Those are not footnotes to hide. They define the next experiments.

A useful follow-up is a private repository accessed through short-lived delegated GitHub authority, then a second independent capability such as a database. If those permissions can be granted, audited, and revoked separately without turning the agent into a credential store, the boundary survives contact with a more realistic workload.

## The principle

Agent security will need prompt-injection defenses, evaluations, model improvements, and careful tool design. None of those should carry the full burden of authorization.

Authorization is infrastructure.

A prompt can request authority. It should not grant authority.

A model can select an action. It should not be the final judge of whether that action is permitted.

And an agent can be extremely capable without permanently possessing the credentials behind every capability it can invoke.

> **Give agents narrowly delegated capabilities. Keep authority outside the reasoning loop.**

The next post moves one layer down the stack: if authority belongs outside the loop, **what exactly should the loop run inside?** That is where the agent harness starts to look less like an application framework and more like a runtime.
