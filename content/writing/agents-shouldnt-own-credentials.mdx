Give an agent a real job and the credential problem appears almost immediately.

We want a small agent that can take a **public GitHub repository**, inspect the code in an isolated environment, and return an architecture and risk briefing. It needs compute and a model. It does not need to become a vault.

Yet the default implementation often starts here:

```env
OPENAI_API_KEY=...
GITHUB_TOKEN=...
DATABASE_URL=...
```

That is convenient for a demo. It is a poor default for software whose defining feature is that it can decide what to do next.

> **Useful agents need capabilities. They do not need to own the credentials behind those capabilities.**

## Deploy the experiment

**[Deploy the experiment →](https://vercel.com/new/clone?repository-url=https%3A%2F%2Fgithub.com%2FSteveVezina%2Fsvezina.dev&root-directory=examples%2Fsecretless-agent&project-name=secretless-repo-analyst)**

The example deliberately does one thing: paste a public GitHub repository URL and get a fast technical briefing.

There is no GitHub token because the repository is public. More importantly, the deployed application does not need an OpenAI or Anthropic provider key. On Vercel, AI Gateway can authenticate the workload using Vercel OIDC.

The flow stays small enough to inspect:

```text
browser
  │
  ▼
Next.js route
  │
  ├── Vercel Sandbox ── clone + inspect public repo
  │
  └── AI Gateway ────── architecture + risk briefing
            ▲
            │
       Vercel OIDC
```

The repository is cloned into an ephemeral Vercel Sandbox. The agent collects a bounded view of the project there instead of executing repository code inside the application process. That separation matters: untrusted work should not inherit application authority simply because an agent chose to run it.

## The `.env` should not be the trust model

As agents become useful, they accumulate access: source code, databases, issue trackers, cloud APIs, production telemetry, internal tools.

If every new capability becomes another permanent secret in the same runtime, we eventually combine three responsibilities in one place:

- deciding what action to take
- executing potentially untrusted work
- holding the credentials that authorize the action

That is an uncomfortable security boundary.

A better decomposition is boring infrastructure:

- **Reasoning:** agent/model layer
- **Execution:** isolated sandbox
- **Model authorization:** gateway + workload identity
- **SaaS authorization:** delegated connection layer
- **Policy:** outside the agent loop
- **Permanent secrets:** ideally absent from the agent runtime

The important property is not that secrets have disappeared from the universe. They have not. The property is that the autonomous workload does not become the long-lived owner of them.

## What “secretless” means here

For this experiment, secretless means **no long-lived model-provider credential is stored by the deployed agent application**.

That distinction matters. The public-repository constraint intentionally avoids pretending we have solved GitHub authorization. Private repositories are the more interesting next step, because the easy answer is to add `GITHUB_TOKEN` and hand permanent authority back to the agent.

I would rather give the agent short-lived, delegated access for a specific identity and task, with policy and revocation outside the loop.

The same pattern should extend to databases, Linear, Slack, cloud APIs, and internal services.

## Capability without ownership

Infrastructure has spent years replacing static cloud credentials with workload identity, short-lived tokens, and explicit trust relationships. Agents should inherit that progress rather than reset it because `.env` is easy.

The experiment is intentionally small. The principle is not:

> **Give agents narrowly delegated capabilities. Keep authority outside the loop.**
