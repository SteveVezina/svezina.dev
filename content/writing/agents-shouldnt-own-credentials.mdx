Most agent demos begin by teaching the application a bad habit.

```env
OPENAI_API_KEY=...
GITHUB_TOKEN=...
DATABASE_URL=...
```

It is convenient. It is also the wrong default for software whose defining feature is that it can decide what to do next.

The more useful an agent becomes, the more systems it can touch. Source code. Databases. Issue trackers. Cloud APIs. Production telemetry. Eventually the agent is not a chat box. It is a workload with authority.

> **How much permanent authority should an autonomous workload own?**

My preferred answer is as close to zero as we can reasonably get.

## A deliberately small experiment

The task is simple: **paste a public GitHub repository URL and get a fast architecture briefing.**

The service creates an ephemeral Vercel Sandbox, clones the repository there, collects a bounded view of the project, then asks a model through Vercel AI Gateway to explain the architecture, important boundaries, and likely operational risks.

The deployed application does not need an OpenAI or Anthropic API key. On Vercel, AI Gateway can authenticate the application with the workload's OIDC identity. The model provider credential is therefore not an application secret.

The Sandbox is intentionally isolated from the parent application's environment. Code being inspected does not inherit application secrets simply because an agent decided to execute something.

```text
browser
  │
  ▼
Next.js route
  │
  ├── Vercel Sandbox ── clone + inspect repo
  │
  └── AI Gateway ────── architecture briefing
            ▲
            │
       Vercel OIDC
```

## The principle is separation

A useful agent needs **capability**. That does not mean it should own the credentials that create that capability.

- **Reasoning:** agent/model layer
- **Execution:** isolated sandbox
- **Model authorization:** gateway/workload identity
- **SaaS authorization:** delegated connection layer
- **Policy:** outside the agent loop
- **Permanent secrets:** ideally nowhere in the agent runtime

When these concerns collapse into one process with a large `.env`, the agent becomes both decision-maker and credential vault.

Secretless does not mean secrets stopped existing. It means the long-lived privileged secret is not owned by the deployed agent workload.

## What this does not solve

Private repositories are where the argument becomes more interesting. The wrong next step would be to add `GITHUB_TOKEN` to project secrets and hand it to the agent. The better direction is delegated, short-lived access minted for a specific user and task, with policy and revocation outside the agent runtime.

The same argument applies to databases, Linear, Slack, cloud APIs, and internal services.

## Capability without ownership

Infrastructure has spent years moving away from static cloud credentials toward workload identity, short-lived tokens, and explicit trust relationships. Agents should not reset that progress because `.env` is easy.

> **Give agents narrowly delegated capabilities. Keep authority outside the loop.**
